# Repository scripts

## Which language

- **Node** (`.mjs`) for repository tooling and CI gates. Node is on every CI runner and every
  workstation that builds the web app, and needs no install step.
- **.NET** for anything that drives a browser or judges a running server: the contract suite, the E2E tests and
  the packaged live audit are projects under `apps/server`, not scripts.
- **No Python.** `check-no-python.mjs` fails CI if a `.py` file is tracked.
- **PowerShell** only for Windows packaging and checks that exercise the Windows package, which includes the VM scenario suite (`scenarios/`): it installs the package on a clean Windows machine and drives it, and runs in Windows PowerShell 5.1 because that is all the VM has.

A new script follows these rules. A script in the wrong language is replaced when it next needs real
work, not rewritten for its own sake. Scripts are named in kebab-case.

## Local development

| Script | What it does |
| --- | --- |
| `scenarios-in-ci.mjs` | Runs one shard of Weir's scenarios. A Linux shard runs against the Docker image CI built (`node scripts/scenarios-in-ci.mjs weir-only --candidate <image>`): the shipped `compose.yaml`, a first account made as an operator makes it (except on a shard whose scenarios need none), then each ported scenario on its own, judged on what it shows and on what System > Logs gained. Its parts are in `scenarios-ci/` (`homes.json` says each scenario's home and state; `shards.mjs` says what each shard runs and how its stack starts, `weir-only.mjs` and `first-visit-account.mjs` hold the ported scenarios; `film.mjs`, `container-box.mjs`, `browser.mjs` (Chromium under Playwright, installed from `scenarios-ci/package.json` only by the shard that needs it), `log-watch.mjs`, `run.mjs`; `images.json` pins every other image the shards start by digest and `with-deluno/` holds the Compose file, the API clients, the scenarios and `fixture/` (the small release source that offers a film to Deluno as a torrent) of the shard that runs Deluno and qBittorrent beside Weir; `fake-world.mjs` and `fake-fresh-world.mjs` are the stand-ins for Weir, the container and the browser that the `scenarios-in-ci*.test.mjs` files run them against; `windows-install.mjs` holds the Windows shard's scenarios, `windows-machine.mjs` is the PC they install on, `windows-shard.mjs` runs the shard, `csrf-signature.mjs` checks the server signs with the secret on disk, and `fake-windows.mjs` is the stand-in for the runner that `scenarios-in-ci-windows.test.mjs` runs them against). | `scenarios-in-ci.test.mjs` | The scenarios in CI without Docker: every scenario of the catalogue has one home and the plan's table says the same, the film and its checks, what the logs gained, the ported scenarios against the stand-in (each way they must fail included), the box's shell commands, and that the workflow's matrix and path filter match. |

## Windows packaging and live audits

| Script | What it does |
| --- | --- |

| `smoke-windows-recover.ps1` | The lock-out recovery through the packaged `WeirServer.exe recover` (PLAT-20): makes an account, a setting and a signed-in session through the API, stops Weir, runs the command's help, account list and a reset, and starts Weir again. The full browser and API audit of a packaged server (Docker or Windows) is not a script: it is
