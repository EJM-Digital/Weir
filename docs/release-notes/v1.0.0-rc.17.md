# Weir v1.0.0-rc.17

Date: 2026-10-14

> **Early days.** Weir is early, and it is in active, hard testing. Expect rough edges. If something is wrong or confusing, please report it on [GitHub issues](https://github.com/jampat000/Weir/issues).

This release candidate fixes a Windows update that could leave Weir not running, makes Weir's start-up watch itself and try again when a start goes wrong, and makes the tray count its server ready only when that same server says it is. It also carries everything from the release candidates before it: how Weir answers a download your media manager sends twice, picking a file back up when it comes back, keeping an imported film from slipping back to "Waiting", and a new border on Weir's icon. Release candidates 14, 15 and 16 were never published. Release candidate 14 was held back because the scenario run on a clean machine found problems in the run itself. Release candidate 15 was held back because that run then found that updating from release candidate 13 could leave Weir not running. Release candidate 16 was held back because that run then found that on a busy machine Weir could freeze for up to 84 seconds on list requests, so a waiting file was judged too early. Everything in all three is here, and release candidate 17 is the first published tag to carry the changes for issues #954, #955, #956 and #958, each confirmed on evidence from the clean-machine run.

## The request stall

On the clean-machine run of release candidate 16, Weir froze for up to 84 seconds on list requests, and a file that was waiting for its media manager was judged too early. Release candidate 17 fixes the cause that was found, and adds a warning that will record the stall if it ever comes back.

- **The cause.** Release candidate 16 made Weir and its tray look again, up to five times 20 milliseconds apart, at a file that seemed to be damaged or missing. Most of those small files are missing most of the time, for example the update state before the first update step, the update settings and network choice on a fresh install, and a pause request after it is answered. So every read of the update state or settings slept four times on a thread that was also serving requests. Weir's pool of threads starts with one thread per processor and adds another only every half second or so, so on a machine with few processors those sleeping reads used up the threads and unrelated requests had to wait behind them.
- **Missing means missing.** A name that is not there is now the answer at the first look. Weir and its tray replace these files by renaming a new file over the old one, which leaves the name in place: 43,000 renames against three readers at once never showed a missing name. Only a file that is refused (a virus scanner holding it, or a rename in progress) is looked at again.
- **Requests look once.** Everything Weir reads while answering a request or running a timer now looks once and keeps the last good reading: the tray's heartbeat, the update state, the reason an update was held back, the update settings and the network choice. A refused file is answered with that last reading, and the next read looks again. Before any reading exists, the safe side is used as before: update settings notify only, and the network choice is this PC only. Only start-up and the tray's watchers, which have nothing else to do, still wait between looks.
- **A warning when work waits for a thread.** When work waits two seconds or more for a thread, Weir writes a warning to **System › Logs** with the pool's counts (threads, how many it starts at once, work waiting, processors). It repeats every 30 seconds while the wait lasts and writes a line when it ends. It runs on a thread of its own, so a starved pool cannot silence it. A test also keeps the list of places in Weir that sleep short, so a new one cannot slip in unnoticed.
- **Measured before and after.** On a 2-processor server with 24 clients asking at once, release candidate 16 answered the update state with a median of 255 ms, the files list took up to 1,012 ms, and the server handled 923 requests in a minute. With this change the update state's median is 5 ms, the files list takes at most 38 ms and the server handles 2,184 requests in a minute, the same as before release candidate 16 made it look again.
- **What was not shown.** The full 84-second stall seen on the clean machine was not reproduced here. The slowdown above was, and removing its cause brings the measurements back to where they were, but the 84 seconds itself is not proven to have the same cause. If it comes back, the new warning will record it in **System › Logs** with the pool's counts, and the clean-machine run will show it.

## What Changed

- **An update can no longer leave Weir not running.** On the clean-machine run, updating from release candidate 13 once left Weir started but never answering: it wrote nothing to its log, did not listen on its port and did not exit. The cause was found by measurement. If the server's printed output went into a pipe that was full and that nobody was reading, the server waited on that pipe before it wrote its first log line. Weir's console output no longer waits: it goes through a small queue handled on its own thread, and if nothing reads it, lines are dropped and counted instead of stopping the server. `weir.log` always keeps every line. A test starts the real server with a full pipe that nobody reads; it failed before this change and passes now. How that server came to have an unread pipe was not found, which is why the start-up watch below is there as well.
- **Weir's start-up now watches itself and tries again.** The tray starts the server, whether it is the first start, a start after a crash or **Restart Weir**, and watches how far it gets. The server reports each step: starting, opening the database, saving a copy of your data, updating the database, getting ready, starting to listen, ready. A start counts as stuck only when the reports stop for longer than that step allows, so a large database that is still working is left alone and a stuck one is not waited on for long. A stuck server is asked to stop and then ended, and only a server the tray itself started is ever touched. The next try does not begin until the old server is confirmed gone; if one cannot be ended, the tray stops there rather than start a second server beside it, and its log names the process to end. Otherwise the start is tried again after a short, growing wait. The details, and the measurements behind the numbers, are in `docs/start-supervision.md`.
- **The tray counts its server ready only when that same server says so.** The tray asks Weir's `/ready` address whether Weir is up, but that address cannot say which Weir answers. If another Weir already held the port, it answered "ready" while the server the tray had just started was about to fail to take the port and exit, and the tray took that answer for its own server's. The tray now accepts a ready answer only after the server it started has reported that it is ready, either on its standard output or in `startup-progress.json`, in a report that carries that server's own process number. A server that exits instead ends the start as any exit does, and one that never reports is treated like any other silent start.
- **A download sent twice gets the right answer.** When your media manager sends the same download again, the new send takes over Weir's work and is told the result with the cleaned file; the earlier send is told it was replaced. Notes no longer mix, so a film never reads "imported" and "will not import" at once. Answers go only to the connection that sent the download. Addresses #955, #956.
- **A file that comes back is picked up again.** A file Weir saw as gone is looked at again as soon as it is back, instead of waiting ten minutes, and its hand-off is answered. Addresses #956.
- **An imported film stays imported.** A film your media manager imported no longer slips back to "Waiting for your media manager" after its download is cleaned up or handed over again.
- **Two connections sharing a download folder.** A file Weir is already working on for one connection is not taken for another; that connection is told Weir is busy and sends it again later.
- **A new logo border.** The Weir app icon, tray icon, browser icon and docs icon now carry a thin teal border set in from the rounded edge, like Deluno's, and the mark is a little smaller so it clears the border. Addresses #958.

## What You See When A Start Goes Wrong

- While Weir is retrying, the tray icon shows Starting.
- If Weir has not started after 5 tries within 15 minutes, the tray stops trying. The icon turns red and a notice says "Weir didn't start after 5 tries, so it has stopped trying. The details are in the tray log. Click to try again." Clicking the notice, or choosing **Restart Weir**, starts over with a fresh set of tries.
- If Weir was running, stopped and could not be brought back, the notice says it stopped and did not start again after that many tries, with the same way back.
- If the port Weir saved last time cannot be read when it starts (another program has the file for a moment), the tray treats that as a failed try like any other: it waits and tries again with the same growing wait, shows Starting, and never asks for a port or saves one meanwhile. After 5 tries it gives up with the same notice, red icon and Restart Weir.
- If Weir was started by something with nobody at the desktop, such as an installer, the tray exits with code 1 and the reason is in the tray log.
- A server that stopped for a reason that trying again cannot change is not tried again: its settings are not valid, it cannot use its database, or it could not save a copy of your data before updating. Its own words are shown, as before.
- If Weir only started on a retry, it works, and **System › Logs** shows a warning that it needed one.

## Where The Logs Are

On Windows, in `C:\ProgramData\Weir`:

- `tray-host.log` says what the tray did: every start attempt with its number, why it failed and how long it waits before the next, and, when a server never answered, a description of the stuck process (how long it ran, its processor time, threads and memory, and the files it had loaded).
- `server-host.log`, next to it, is new. It keeps everything the server printed while it started and anything it wrote to its error output, each line marked with the server's process number. It keeps one earlier file, up to 1 MB each.
- `logs\weir.log` now says Weir is starting before anything that could block, then that it is opening the database, so a start that stops leaves how far it got.
- `startup-progress.json` holds the latest step the server reported.

## Fixes And Stability

- **A file that is being replaced is no longer taken for a damaged or missing one.** Weir and its tray pass small files to each other, and each is replaced by renaming a new file over the old. A reader that looked at that instant could be refused, and a virus scanner holding a freshly written file does the same. The tray could then read the saved network choice as "this PC only" and restart the server, act on update settings that were not there, start the wait for Weir to be idle over, ask the first-run port question again and save another port over yours (it now waits and tries again, as for any other start), or send an update on as if Weir could not save a copy of its data. The server could briefly report that the tray had quit, that a downloaded update was gone, or drop a pause or backup request. A reader that is refused now looks again before it says anything, and a file that stays refused is treated as "not yet": it keeps the last thing known, or waits, and changes nothing. A name that is not there is simply not there; see the request stall above.
- **A failed browser test now keeps its evidence.** One end-to-end browser test, `SeededModuleSaveTests.Saved_state_persists_across_settings_and_processing`, failed once in a full run on the way to release candidate 15, and its error was not kept. It did not come back in many later runs, with the order of steps, folder deletes and a fully loaded processor forced, and no fault in Weir was found, so its cause is not proven and it is not set aside. Every browser test now records a trace and its browser and server logs, and a test that fails keeps its full error, the trace, the logs and a screenshot of each page under `artifacts/e2e-failures`. A passing test deletes its own, and the build uploads the folder as `e2e-failure-evidence`, including for a test that passed only on its retry.
- **Every release is proven before it is tagged.** A scenario run on a clean machine — install, update, first visit, real hand-offs from Deluno, pause, Process again, a deleted file and Logs — must pass on the exact commit before any release, release candidates included, can be published. Addresses #954.
- **The scenario run is now done in three steps around Deluno's suite.** First the build is installed over the Weir that Deluno's own installer put there, before Deluno sends any film; then, once Deluno's suite has made its hand-offs, the Deluno scenarios run; then the clean-machine scenarios run on a restored clean checkpoint. Each Deluno hand-off is judged by the Weir that handled it, so a hand-off the previous release answered is counted but never held against the new build. The checks for the update, resent hand-offs, small extras and Deluno's outcome records were corrected against what the first run showed, and a step that goes wrong no longer stops the next one. The run's Logs check also fails when a start needed a retry, unless the run names it.
- **The Docker start-up check no longer ends without a result.** When the container's health address hung, the check could end with no retry and no container log. A hung attempt now counts as a failed attempt, the check tries again, and the container's log is printed if every attempt fails.
- **The contract suite no longer mistakes one server for another.** The suite picks a free port, releases it and starts a server on it. Two starts that picked the same port could both launch; one won and the other exited with "address already in use", but its start-up had already read the winner's "ready" and taken it for its own, so a test ran against another test's server. A server now counts as ready only when its address answers and the process the suite started has logged that it listens on its port. The loser is seen to exit and is started again on a new port. Tests cover a port held by another Weir server and four servers picking one port at once; both failed before the change.
- **A failed contract test keeps the logs of its own servers.** Each server copies its `weir.log`, its standard output and error and its progress file when it stops, into a folder named for the test that used it (`artifacts/contract-failures`). A server shared by the tests of one class is kept under the class name. A passing test deletes its folder, and CI uploads the rest as `contract-failure-evidence-<area>`.
- **One more test no longer assumes a fast machine.** A test of the start-up refusal message read the console before its last line had reached it; on a busy runner it read nothing. It now waits for the line, with a ceiling.
- Two tests that measured time against the real clock now use their own clock, so a busy machine no longer fails them; Weir's real time limits were confirmed safe.
- The copyright line now reads "Copyright (C) 2026 jampat000 and the Weir contributors".

## Upgrade Notes

- Windows: **Check now** then **Download update** then **Restart and apply** in System › About, or install `Weir-win-Setup.exe` over the top. Before installing, Weir saves a copy of its data. Two database updates run on first start.
- Anything that starts Weir and then waits for it to answer should allow about three minutes for a Weir that has to retry, and longer for a very large database. A start that goes well still takes a few seconds.
- Docker: change the image to `ghcr.io/jampat000/weir:1.0.0-rc.17`, then `docker compose pull && docker compose up -d`.
