# Weir v1.0.0-rc.16

Date: 2026-10-13

> **Early days.** Weir is early, and it is in active, hard testing. Expect rough edges. If something is wrong or confusing, please report it on [GitHub issues](https://github.com/jampat000/Weir/issues).

This release candidate fixes a Windows update that could leave Weir not running, and makes Weir's start-up watch itself and try again when a start goes wrong. It also carries everything from the two release candidates before it: how Weir answers a download your media manager sends twice, picking a file back up when it comes back, keeping an imported film from slipping back to "Waiting", and a new border on Weir's icon. Release candidates 14 and 15 were never published. Release candidate 14 was held back because the scenario run on a clean machine found problems in the run itself. Release candidate 15 was held back because that run then found that updating from release candidate 13 could leave Weir not running. Everything in both is here.

## What Changed

- **An update can no longer leave Weir not running.** On the clean-machine run, updating from release candidate 13 once left Weir started but never answering: it wrote nothing to its log, did not listen on its port and did not exit. The cause was found by measurement. If the server's printed output went into a pipe that was full and that nobody was reading, the server waited on that pipe before it wrote its first log line. Weir's console output no longer waits: it goes through a small queue handled on its own thread, and if nothing reads it, lines are dropped and counted instead of stopping the server. `weir.log` always keeps every line. A test starts the real server with a full pipe that nobody reads; it failed before this change and passes now. How that server came to have an unread pipe was not found, which is why the start-up watch below is there as well.
- **Weir's start-up now watches itself and tries again.** The tray starts the server, whether it is the first start, a start after a crash or **Restart Weir**, and watches how far it gets. The server reports each step: starting, opening the database, saving a copy of your data, updating the database, starting to listen, ready. A start counts as stuck only when the reports stop for longer than that step allows, so a large database that is still working is left alone and a stuck one is not waited on for long. A stuck server is asked to stop and then ended, and only a server the tray itself started is ever touched. The start is then tried again after a short, growing wait. The details, and the measurements behind the numbers, are in `docs/start-supervision.md`.
- **A download sent twice gets the right answer.** When your media manager sends the same download again, the new send takes over Weir's work and is told the result with the cleaned file; the earlier send is told it was replaced. Notes no longer mix, so a film never reads "imported" and "will not import" at once. Answers go only to the connection that sent the download. Addresses #955, #956.
- **A file that comes back is picked up again.** A file Weir saw as gone is looked at again as soon as it is back, instead of waiting ten minutes, and its hand-off is answered. Addresses #956.
- **An imported film stays imported.** A film your media manager imported no longer slips back to "Waiting for your media manager" after its download is cleaned up or handed over again.
- **Two connections sharing a download folder.** A file Weir is already working on for one connection is not taken for another; that connection is told Weir is busy and sends it again later.
- **A new logo border.** The Weir app icon, tray icon, browser icon and docs icon now carry a thin teal border set in from the rounded edge, like Deluno's, and the mark is a little smaller so it clears the border. Addresses #958.

## What You See When A Start Goes Wrong

- While Weir is retrying, the tray icon shows Starting.
- If Weir has not started after 5 tries within 15 minutes, the tray stops trying. The icon turns red and a notice says "Weir didn't start after 5 tries, so it has stopped trying. The details are in the tray log. Click to try again." Clicking the notice, or choosing **Restart Weir**, starts over with a fresh set of tries.
- If Weir was running, stopped and could not be brought back, the notice says it stopped and did not start again after that many tries, with the same way back.
- If Weir was started by something with nobody at the desktop, such as an installer, the tray exits with code 1 and the reason is in the tray log.
- A server that stopped for a reason of its own, such as being unable to save a copy of your data before updating, is not tried again. Its own words are shown, as before.
- If Weir only started on a retry, it works, and **System › Logs** shows a warning that it needed one.

## Where The Logs Are

On Windows, in `C:\ProgramData\Weir`:

- `tray-host.log` says what the tray did: every start attempt with its number, why it failed and how long it waits before the next, and, when a server never answered, a description of the stuck process (how long it ran, its processor time, threads and memory, and the files it had loaded).
- `server-host.log`, next to it, is new. It keeps everything the server printed while it started and anything it wrote to its error output, each line marked with the server's process number. It keeps one earlier file, up to 1 MB each.
- `logs\weir.log` now says Weir is starting before anything that could block, then that it is opening the database, so a start that stops leaves how far it got.
- `startup-progress.json` holds the latest step the server reported.

## Fixes And Stability

- **A failed browser test now keeps its evidence.** One end-to-end browser test, `SeededModuleSaveTests.Saved_state_persists_across_settings_and_processing`, failed once in a full run on the way to release candidate 15, and its error was not kept. It did not come back in many later runs, with the order of steps, folder deletes and a fully loaded processor forced, and no fault in Weir was found, so its cause is not proven and it is not set aside. Every browser test now records a trace and its browser and server logs, and a test that fails keeps its full error, the trace, the logs and a screenshot of each page under `artifacts/e2e-failures`. A passing test deletes its own, and the build uploads the folder as `e2e-failure-evidence`, including for a test that passed only on its retry.
- **Every release is proven before it is tagged.** A scenario run on a clean machine — install, update, first visit, real hand-offs from Deluno, pause, Process again, a deleted file and Logs — must pass on the exact commit before any release, release candidates included, can be published. Addresses #954.
- **The scenario run is now done in three steps around Deluno's suite.** First the build is installed over the Weir that Deluno's own installer put there, before Deluno sends any film; then, once Deluno's suite has made its hand-offs, the Deluno scenarios run; then the clean-machine scenarios run on a restored clean checkpoint. Each Deluno hand-off is judged by the Weir that handled it, so a hand-off the previous release answered is counted but never held against the new build. The checks for the update, resent hand-offs, small extras and Deluno's outcome records were corrected against what the first run showed, and a step that goes wrong no longer stops the next one. The run's Logs check also fails when a start needed a retry, unless the run names it.
- **The Docker start-up check no longer ends without a result.** When the container's health address hung, the check could end with no retry and no container log. A hung attempt now counts as a failed attempt, the check tries again, and the container's log is printed if every attempt fails.
- Two tests that measured time against the real clock now use their own clock, so a busy machine no longer fails them; Weir's real time limits were confirmed safe.
- The copyright line now reads "Copyright (C) 2026 jampat000 and the Weir contributors".

## Upgrade Notes

- Windows: **Check now** then **Download update** then **Restart and apply** in System › About, or install `Weir-win-Setup.exe` over the top. Before installing, Weir saves a copy of its data. Two database updates run on first start.
- Anything that starts Weir and then waits for it to answer should allow about three minutes for a Weir that has to retry, and longer for a very large database. A start that goes well still takes a few seconds.
- Docker: change the image to `ghcr.io/jampat000/weir:1.0.0-rc.16`, then `docker compose pull && docker compose up -d`.
